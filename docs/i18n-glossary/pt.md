# Portuguese glossary — `bitshares-vanilla-ui`

This is the file an external auditor reads **before** trusting a machine-filled
Portuguese translation. It fixes **one Portuguese term per concept**, so a
single correction here (plus the same word in `vanilla/locales/pt.json`)
propagates everywhere instead of leaving three near-synonyms in the UI.

**How to use it**

- Translate the English term in column 1 as the Portuguese term in column 2. Do
  not invent a second Portuguese word for the same concept: a synonym split is
  the one mistake this file exists to prevent.
- Column 3 says why, and names the `pt.json` keys that already prove the
  wording. Keys cited there were read out of `vanilla/locales/pt.json` after
  the 2026-10-13 chunk-B3 fill, which was the pass that closed the last 270
  untranslated keys (105 translated, 165 kept byte-identical to English on
  purpose — see `tooling/apply_i18n_pt_chunkB3.py`). A citation is evidence,
  not decoration. In the notes, a Portuguese WORD in bold is a form under
  discussion, not a locale key — only things shaped like `section.key` are
  citations.
- Corrections land through the `translation` issue label on the project tracker —
  the same route `#/help/translation-limitations` in the wallet gives readers.
- **Status:** the Portuguese column below is the agreed vocabulary, not yet a
  claim of human review. Every fill pass cross-checked its row against
  `pt.json` and chose the form that file actually uses. Until a person has read
  a string in Portuguese, the wallet labels it machine-filled
  (`i18n.badge_label`).
- **Every row names the form `pt.json` uses.** Where a second form exists for
  the same concept, the row lists **every** string carrying it — as a
  counter-example (align it on the next pass) or as a same-root other sense
  (leave it alone). A glossary that breaks a dozen correct pool strings is worse
  than no glossary. Counts are of the agreed Portuguese WORD, and they only
  count strings that actually differ from English: a loanword is legitimately
  identical to English and is not evidence of a translation.

**Variant: `pt.json` is BRAZILIAN Portuguese.** That is settled, not a
preference: the already-translated dictionary is informal and Brazilian in
`você` ("Navegue nos mercados de graça", `splash.hero_sub2`), in the imperative
on-ramp lines ("Trocar senha", `wallet.console_change_password`),
and in vocabulary that is Brazilian rather than European (`carteira` for the
wallet, `troca` for barter, `painel` for the dashboard, `cota` for a share,
`saldo` for a balance, `nó` for a node, `emissor` for an issuer). No
European-Portuguese (`carteira`→`porta-festas`, `cota`→`unidade`,
`nó`→`nodo`, `utilizador`, `cambial`) or formal-register (`você`→`o senhor`,
`a Carteira`) spelling appears anywhere in the shipped file. Keep it that way:
this batch's strings were written to match, and a European form landing in one
signing dialog is exactly the kind of drift this file exists to catch.

Placeholders (`%(name)s`), URLs, object ids (`1.2.x`), asset symbols, op
numbers and theme or network ids are **byte-verbatim** in every language and
never appear here.

**Typography: `pt.json` ships ZERO apostrophes.** Portuguese needs none for
possession or contraction in this dictionary's register ("sua conta", not
"sua' conta"), and none of the thousands of translated strings carries an ASCII
or typographic one. `tooling/apply_i18n_pt_chunkB3.py` refuses to add either
(gate G7), so an apostrophe appearing in a Portuguese string is a bug a reviewer
should report rather than a spelling to preserve.
